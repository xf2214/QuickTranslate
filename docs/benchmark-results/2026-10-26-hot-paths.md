# 2026-10-26 热路径微基准

## 范围与结论

本报告测量真实 50 万条 packed 词典的解析 / 索引构造、成员查询和 CTC 输出读取。**不包含 ONNX 推理、截屏、WPF、网络或识别准确率。** 分配量是执行线程累计托管分配，不是进程驻留内存或峰值工作集。

主要可确认收益：词典加载分配减少 **36.7%**；OCR 仅查询成员时基本不再为译文对象分配；连续 CTC 输出消除约 23.95 MB 的数组复制。

## 最终测量

环境：Ubuntu 24.04.3 LTS、X64、8 个逻辑处理器、.NET 10.0.11，Release。停止并行构建与测试后顺序运行优化版和原版。容器仍是共享计算环境，数字不应当作 Windows 桌面的延迟承诺。

### 词典：真实原版 / 修改版生产程序集

| 指标 | 原版 | 修改版 |
|------|-----:|-------:|
| 加载 P50（ms） | 413.12 | 357.89 |
| 加载 P95（ms） | 821.81 | 565.67 |
| 加载托管分配（MB，十进制） | 224.59 | 142.22 |
| 普通 TryLookup P50（µs） | 0.106 | 0.288 |
| 普通 TryLookup 分配（B/op） | 212.019 | 212.019 |

加载在预先计算文件哈希后执行，因此文件系统缓存已热；每次创建新的词典实例并触发完整解析 / FrozenDictionary 构造，共 5 次。P95 是这 5 次中的最大值，不能视作大量启动样本的尾延迟。原版来自改动前保存的生产 DLL，提交为 `4859c4527bda0d582b47a3d0503ded40feb7c9e1`。

修改版的普通 TryLookup 在这次测量中没有更快。本次为 OCR 新增的是成员查询；不把普通译文查询宣称为提速。微秒以下的时间还受 JIT、哈希表布局和共享 CPU 调度影响，分配变化比这类时间比率更稳定。

### 同一修改版进程内：OCR 成员查询

| 操作 | P50（µs/op） | P95（µs/op） | 托管分配（B/op） |
|------|------------:|------------:|----------------:|
| TryLookup，构造译文结果后丢弃 | 0.288 | 0.496 | 212.019 |
| ContainsWord，仅查询是否存在 | 0.095 | 0.132 | 0.0032 |

固定使用 5 个命中词和 1 个未命中词，均为已规范化的小写输入；25 个批次，每批 10,000 次。该结果不代表任意大小写 / 空白输入也绝对零分配，NormalizeKey 仍可能为输入规范化分配字符串。

### 同一修改版进程内：CTC 输出复制

| 路径 | P50（ms） | P95（ms） | 托管分配（B/op） |
|------|----------:|----------:|----------------:|
| ToArray 后解码 | 21.48 | 29.08 | 23950845 |
| 直接读取 Tensor 解码 | 14.08 | 18.07 | 1248 |

使用 `[1,320,18710]` 合成连续输出，共 23,948,800 字节；两条路径共用同一个解码器，8 次预热后各取 31 个样本，仅隔离被移除的输出复制。概率 / blank 序列是合成输入，不是截图推理输出。P50 在本次运行下降 34.4%，**不能换算成完整 OCR 提速百分比**。

## 探索测量与波动

保留了整合时仍有并行构建 / 测试的 [原版记录](2026-10-26-exploratory-baseline.json) 和 [修改版记录](2026-10-26-exploratory-optimized.json)。那一轮加载 P50 是 588.30 → 797.81 ms，方向与停止并行任务后的复测不同；两轮加载分配均约 224.6 → 142.2 MB。因此本轮以可重现的分配减少为主要收益，时间数据完整披露，不以单次微基准保证用户机器上的加速倍数。

## 复现

在仓库根目录执行：

```sh
dotnet build benchmarks/QuickTranslate.HotPathBenchmarks/QuickTranslate.HotPathBenchmarks.csproj -c Release -p:EnableWindowsTargeting=true
dotnet run --project benchmarks/QuickTranslate.HotPathBenchmarks/QuickTranslate.HotPathBenchmarks.csproj -c Release --no-build -- assets/dictionaries/ecdict-lite.packed
```

harness 必须传入名为 `ecdict-lite.packed` 的有效文件，其父目录不能含 `custom-dictionary.txt`，以便哈希对象与实际加载对象一致。加载前完整哈希文件的行为是有意的。

本次原版对照的做法：在改动前保留基线生产 `QuickTranslate.Core.dll` 与 `QuickTranslate.Infrastructure.dll`；复制同一份已构建 harness 输出到隔离目录，仅替换这两个 DLL，再运行同一个词典文件。成员查询通过预先绑定的反射 delegate 探测，因此原版没有 ContainsWord 也能运行。CTC decoder 作为源码链接到 harness，两个进程中的复制 / 直接读取实验都使用同一解码算法；不能把原版 JSON 中出现 direct_tensor 指标理解成旧产品已经采用该路径。

基准不作为 CI 的机器速度断言。正确性回归与本报告的性能测量分开。
