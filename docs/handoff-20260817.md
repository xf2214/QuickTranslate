> 本文档记录最近一轮集中修复与功能迭代的全过程：OCR 无法正确识别的根因修复、
> 翻译大模型改为自定义 OpenAI 兼容接入、识别/翻译加载动画、弹窗尺寸自适应等。

## 一、项目概览

QuickTranslate 是一个 Windows WPF 划词/截屏翻译工具：

- **Alt+1**：鼠标取词翻译（词弹窗）
- **Alt+2**：鼠标所在段落区域翻译（块弹窗）
- **Esc**：取消当前操作
- 托盘常驻，设置窗口可改热键/目标语言/翻译引擎等

### 解决方案结构

| 项目 | 职责 |
|------|------|
| `src/QuickTranslate.Core` | 领域抽象（IOcrEngine、ITranslationProvider、ISelectionOverlayService 等）、几何类型（DIP/物理坐标）、AppSettings |
| `src/QuickTranslate.Infrastructure` | OCR 引擎（PaddleOcrV6Engine/MockOcrEngine）、翻译提供方（QwenMt/自定义 OpenAI）、词典/缓存/SettingsManager/ModelDownloader |
| `src/QuickTranslate.Platform` | Win32 互操作（GDI 截屏、热键、DPI、窗口样式） |
| `src/QuickTranslate.App` | WPF 界面（弹窗、选区遮罩、加载指示器、设置窗口）、协调器（Word/Block InteractionCoordinator） |
| `src/QuickTranslate.TextToSpeech` | Windows SAPI 朗读 |
| `tests/QuickTranslate.Tests` | xUnit 测试（当前 **317 个全部通过**） |
| `assets/models` | OCR 模型（det.onnx/rec.onnx/ppocr_keys.txt/version.json） |

### 关键数据流

```
热键 → 协调器（App/Coordination）
     → GdiScreenCapture 截屏（物理像素）
     → IOcrEngine.RecognizeAsync（PP-OCRv6 ONNX：det→cls→rec→CTC 解码）
     → WordSelector / DefaultBlockSelector（屏幕坐标命中测试）
     → ITranslationRouter（L1/L2 缓存 → ECDICT 词典 → ITranslationProvider）
     → ITranslationProvider（Dispatcher → CustomOpenAi（SSE 流式）或 QwenMt（非流式））
     → 弹窗显示（PopupPlacement 定位 + PopupSizeEstimator 尺寸）
```

## 二、本轮修复与功能明细

### 2.1 OCR「无法正确识别」根因修复（最重要）

**症状**：真实 PP-OCRv6 模型在位，但识别结果全是乱码/相邻错字。

**根因（三个叠加）**：

1. **字典与模型错配**：`rec.onnx` 来自 HoVDuc/ppocrv5-onnx v1.1.0（"PP-OCRv6 medium"），
   输出 **18710** 个类别；但程序配套的是 `ppocr_keys_v1.txt`（**6623** 行）。
2. **CTC 标签布局写反**：PaddleOCR 的 CTC 布局是
   `label 0 = blank，1..N = 字典行，N+1（末位）= 空格`；
   旧代码把空格插在**首位**且假设 blank 在**末位** → 即使字典对了，每个字符也会整体偏移一位。
3. **det 归一化通道顺序错误**：PaddleOCR 对 **BGR** 图像按 `[0.485, 0.456, 0.406]` 逐通道归一化
   （B←0.485 的历史怪癖），旧代码按 RGB 归一化 → 检测召回率下降。

**修复内容**（均在 `src/QuickTranslate.Infrastructure/Ocr/PaddleOcrV6Engine.cs`）：

- `BuildCharDictionary`：改为 `[blank 占位, 字典行..., 末位空格]` 布局；
- `CtcGreedyDecode`：`blankIdx = 0`（原来是 `C-1`）；
- `PreprocessDet`：归一化改为 BGR 顺序（有注释警告勿"修正"回 RGB）；
- `DbPostprocess`：DB 阈值改为与模型 `inference.yml` 一致（`thresh 0.3→0.2`、`boxThresh 0.5→0.45`、`unclip 1.5→1.4`）；
- `PreprocessRec`：保持纵横比不拉伸，`RecMaxW 320→1280`（模型支持动态宽度到 3200）；
- 会话初始化时新增**字典长度 vs rec 输出类别数**一致性检查，不匹配打 Warning 日志。

**配套字典文件**：

- `assets/models/ppocr_keys.txt` 已替换为**从 HoVDuc zip 内 `inference.yml` 的
  `PostProcess.character_dict` 提取的 18708 字符版本**（UTF-8 无 BOM，每行一字符）；
- `assets/models/version.json` 的 `keys` 条目已更新（sha256
  `b5f2bfe2bdd9448429e3e82b51c789775d9b42f2403d082b00662eb77e401c5d`，74947 字节）。

**验证**：新增 `tests/QuickTranslate.Tests/RealOcrRecognitionTests.cs`，
用 GDI+ 渲染已知文本（英文单词/英文短语/中文「中文识别测试」/长句）跑**完整识别链路**，
断言识别正确 —— 本机全部通过（此前全部乱码）。

### 2.2 version.json「劫持」误报修复

**症状**：启动日志反复出现
`[ModelVersion] SHA256 mismatch or model missing; fallback to MockOcrEngine`，
但模型实际完好（该警告仅日志层，不实际切换引擎，但会误导排查方向）。

**根因**：App csproj 把 version.json 复制到 `bin\...\models\version.json`，
而 `ModelVersionVerifier.FindVersionJsonPath()` 的候选顺序里 `BaseDirectory/models` 排第一；
该目录只有 version.json 没有 onnx → 所有模型按「缺失/哈希不符」处理。

**修复**：

- `QuickTranslate.App.csproj`：`Link="models\version.json"` → `Link="assets\models\version.json"`
  （与 PaddleOcrV6Engine 的候选目录 `BaseDirectory/assets/models` 对齐）；
- `ModelVersionVerifier`：候选目录必须**实际存在 onnx** 才优先命中；文件缺失改为
  Debug 日志跳过（不算 mismatch），只有「文件存在但哈希不符」才算失败；
- 手动删除了 `bin/Debug/net10.0-windows/models/` 旧劫持目录。

### 2.3 ModelDownloader 重写（新装机路径）

旧下载器的 URL 指向 `paddleocr.bj.bcebos.com/PP-OCRv6/...`（与实际模型来源不符），
且字典 URL 固定拉 6623 行的 v1 字典 → 新装机会复现 2.1 的错配。

`src/QuickTranslate.Infrastructure/Services/ModelDownloader.cs` 已重写：

- det/rec 从 **HoVDuc GitHub Release zip** 下载 → 解压取最大 `.onnx`；
- `ppocr_keys.txt` 由 **rec zip 内 inference.yml 自动生成**（同 URL 只下载一次）；
- cls.onnx 保持 bcebos 直链，改为**可选**（失败仅告警不阻断）；
- 下载完自动把 version.json 复制到模型目录供校验器使用；
- `scripts/download-v6-final.ps1` 同步改为从 yml 生成字典（替换旧的"最大 txt"启发式）。

### 2.4 翻译大模型改为自定义接入（OpenAI 兼容）

**目标**：翻译不再绑定 DashScope Qwen-MT，支持任意 OpenAI 兼容端点
（OpenAI / DeepSeek / Moonshot / 本地 vLLM / Ollama / one-api…）。

**新增/修改**：

| 文件 | 内容 |
|------|------|
| `Core/Options/AppSettings.cs` | 新增 `TranslationProviderKind`（CustomOpenAi=默认 / QwenMt）、`CustomLlmBaseUrl`、`CustomLlmModel`、`CustomLlmMaxContextLines`、`IsCustomLlmConfigured` |
| `Infrastructure/Translation/CustomOpenAiTranslationProvider.cs` | **新增**。POST `{BaseUrl}/chat/completions`，SSE 流式优先、非 SSE 自动回退 JSON；Bearer 鉴权；401/429/5xx 映射 TranslationException；未配置（URL/模型/Key 缺一）降级 Mock 占位流；**配置每次从 AppSettings 单例实时读**（保存即生效，无需重启） |
| `Infrastructure/Translation/TranslationProviderDispatcher.cs` | **新增**。ITranslationProvider 按 `TranslationProvider` 设置路由到 Custom 或 QwenMt |
| `Infrastructure/ServiceCollectionExtensions.cs` | 注册两个 provider + Dispatcher 作为 `ITranslationProvider` |
| `Infrastructure/Persistence/SettingsManager.cs` | 持久化新字段 + 就地更新单例（热生效） |
| `App/Validation/SettingsValidator.cs` | 新增 `ValidateCustomLlm`（http/https 校验、选自定义引擎时必填、填一半必须报错） |
| `App/Windows/SettingsWindow.xaml(.cs)` | S1 卡片扩展：翻译引擎下拉、API 地址、模型名称（带示例提示），API Key 共用 |

**URL 容错**：`BuildChatCompletionsUrl` 自动补尾斜杠/`/chat/completions`；
缺 scheme 时补全（localhost 默认 `http://`，公网默认 `https://`）。

**测试**：`CustomOpenAiProviderTests`（URL 构建/Mock 降级/SSE 流/JSON 回退/401 映射/配置热切换）、
`TranslationProviderDispatcherTests`（按设置路由 + 热切换）、`CustomLlmValidationTests` 共 20 个，全绿。

### 2.5 识别中/翻译中加载动画（反馈优化）

**问题**：按热键后到弹窗出现之间（OCR 首次推理数百毫秒~秒级）无任何反馈，像热键失灵。

**新增**：

- `Core/Abstractions/IStatusIndicatorService.cs`：`Show/Update/Hide`；
- `App/Windows/StatusIndicatorWindow.xaml(.cs)`：深色圆角 pill + **三点跳动循环动画** +
  文案（"正在识别…"/"正在翻译…"）；窗口 `WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOPMOST`
  **完全点击穿透、不抢焦点**；
- `App/Services/WpfStatusIndicatorService.cs`：单窗口复用、自动 marshal 到 UI 线程、
  锚点下方优先/上方回退/工作区钳制定位；
- `Platform/Win32/WindowStyleHelper.SetTopMostNoActivateClickThrough()` +
  `User32.WS_EX_TRANSPARENT` 常量。

**协调器集成**（`WordInteractionCoordinator` / `BlockInteractionCoordinator`，
构造函数以**可选参数**注入 `IStatusIndicatorService? = null`，不破坏既有测试）：
Capturing 阶段 Show("正在识别…") → Translating 阶段 Update("正在翻译…") →
**所有退出路径**（成功/各异常/取消/NoTextFound）Hide。

`AppHost` 已注册 DI。测试：`StatusIndicatorLifecycleTests` 3 个（成功隐藏/出错隐藏/CancelAll 隐藏）。

### 2.6 弹窗文本框大小自适应

**问题**：词弹窗固定 320×150（短译文大片空白、长译文被裁剪）；块弹窗固定 440×480。

**新增** `App/Services/PopupSizeEstimator.cs`：

- 按文本估宽（**CJK≈字号、ASCII≈0.58×字号**），词弹窗 300~520、块弹窗 360~720（工作区比例钳制）；
- 高度按行数增长，钳制工作区 45%/60%，极小屏有下限保护。

**窗口改动**：

- `WordPopupWindow.xaml`：译文区外包 `ScrollViewer MaxHeight=300`（估算失手时的裁剪保险）；
- `BlockPopupWindow.xaml(.cs)`：新增**OCR 原文灰色预览区**（最多 3 行省略，便于核对识别范围）、
  `ResetContent()` 防止窗口复用时旧译文残留；
- 两个弹窗 Service（`WpfWordPopupService` / `WpfBlockPopupService`）改用估算器尺寸。

测试：`PopupSizeEstimatorTests` 5 个；`PopupDipLayoutTests` 期望值改为与估算器同源计算。

- `OcrModelTests` 测试集合依赖进程级环境变量 `QUICKTRANSLATE_DISABLE_DEV_MODEL_PATHS`，
